# Q21. Read Logs from a Specific Container (Intermediate)

## Objective

Retrieve logs separately from each container inside an existing Kubernetes Pod named `two-container-pod`.

The Pod contains:
- `nginx-container`
- `busybox-container`

## Concepts Learned

### 1. kubectl logs

`kubectl logs` is used to retrieve logs generated by a container.

It helps in:
- Monitoring application behavior.
- Troubleshooting application issues.
- Identifying startup errors.
- Debugging containerized applications.

### 2. Container Selection

When a Pod contains multiple containers, use the `-c` option to specify which container's logs you want to retrieve.

## Practical Implementation

### Task 1: Retrieve Nginx Container Logs

Command:

```bash
kubectl logs two-container-pod -c nginx-container
```

Output:

```text
/docker-entrypoint.sh: /docker-entrypoint.d/ is not empty, will attempt to perform configuration
/docker-entrypoint.sh: Looking for shell scripts in /docker-entrypoint.d/
/docker-entrypoint.sh: Configuration complete; ready for start up
2026/11/25 14:10:08 [notice] 1#1: using the "epoll" event method
2026/11/25 14:10:08 [notice] 1#1: nginx/1.31.10
2026/11/25 14:10:08 [notice] 1#1: start worker processes
```

**Explanation:**

Nginx generated startup logs while initializing its configuration and starting worker processes.

### Task 2: Retrieve BusyBox Container Logs

Command:

```bash
kubectl logs two-container-pod -c busybox-container
```

Output:

```text
```

**Explanation:**

The BusyBox container returned empty logs because it was executing a sleep command.

The sleep command does not generate application output on stdout or stderr.

Empty logs do not automatically indicate a Kubernetes failure.

## Comparison of Container Logs

| Feature | Nginx | BusyBox |
|---|---|---|
| Logs | Available | Empty |
| Output | Startup messages | No output |
| Reason | Nginx initialization | Sleep command |
| Expected behavior | Startup logs | Empty logs |

## Logs vs Events

| Logs | Events |
|---|---|
| Generated by container processes | Generated by Kubernetes components |
| Used to inspect application output | Used to inspect cluster activities |
| Shows startup messages and application errors | Shows scheduling and image-pulling activities |
| `kubectl logs` | `kubectl get events` |

## Important Commands

```bash
# Retrieve Nginx logs
kubectl logs two-container-pod -c nginx-container

# Retrieve BusyBox logs
kubectl logs two-container-pod -c busybox-container

# Check Pod status
kubectl get pods

# Inspect Pod events and container details
kubectl describe pod two-container-pod

# View Kubernetes events
kubectl get events
```

## Interview Questions

**1. What is kubectl logs?**

It is a Kubernetes command used to retrieve logs generated by a container.

**2. Why do we use -c with kubectl logs?**

It specifies the particular container when a Pod contains multiple containers.

**3. Why can BusyBox return empty logs?**

Because it is executing a sleep command that does not produce output.

**4. Does empty container output mean the container has failed?**

No. A container can be running successfully without generating logs.

**5. What is the difference between logs and events?**

Logs represent output from container processes, whereas events represent Kubernetes activities such as scheduling, image pulling, and failures.
